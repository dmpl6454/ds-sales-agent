## 1. "I want all paid post detection to work"

Detection is **not** broken — that was measured to death on 17 August (see CLAUDE.md and
<https://claude.ai/code/artifact/3154f55f-2f4c-4f6e-a231-1707f9412424>). Capture is 100%,
and ~12 paid posts a day from @viralbhayani is correct to within ~20%.

What IS broken is narrower and measured. In priority order:

### 1a. 83 posts had their footage read and never reached a verdict

`frame:call-failed` — the classifier call failed and nothing retried. `rejudgeUnusedEvidence`
exists for exactly this and is bounded at 10 per pass, so it drains at 10/day against a
backlog of 83. **Raise the bound or run it deliberately**, and check it still only records
what it actually READ (the `profileStatus` trap: a re-judge run from the Mac must not write
"no frame saved" about frames living on the server).

### 1b. 54% of posts are judged on the caption alone

No footage text at all. CLAUDE.md's own warning is that *a paid placement can live entirely
in the video*. Find out WHY — is the frame not saved, not OCR'd, or OCR'd to nothing? The
five states are already distinguished on `/paid-posts` (`read-with-text` /
`read-no-text` / `no-frame` / `no-engine` / `failed`); read them per channel before changing
anything, because a single low count cannot tell a clean corpus from a broken reader.

### 1c. 13% (119 posts) are auto-ORGANIC by a rule the model never sees

`tooShortToJudge` (caption < 15 chars) files them ORGANIC for free — and **84 of them have
footage text nobody classified.** A one-word caption on a reel whose video carries a title
card is exactly the Thane case. The rule was correct when captions were the only input; it
is not obviously correct now that the footage is read. **Measure before changing:** how many
of those 84 would the frame call escalate? At ~$0.00002 a call that is a few cents to find
out, and it is the single cheapest recall experiment available.

### 1d. The model never hedges — 0 of 518 ORGANIC verdicts below 80% confidence

A model that is never uncertain about a genuinely hard judgement is confident by default,
not calibrated. This matters because the confidence floor is now inert (it never fired
once). Worth knowing before anyone builds anything that trusts a confidence number.

**Do NOT tune the prompt without `pnpm ig:accuracy --repeat 3` before and after.** The
classifier is not deterministic — identical runs swing recall 95-100% — and the prompt is a
module-level constant whose 50x cache discount dies silently if anything is interpolated.

## 3. "Accuracy measured real time"

There is no continuous measurement today. `pnpm ig:accuracy` is a command someone runs, and
*a feature that only works when someone runs a command is not running* — this codebase's own
lesson, learned from 166 cover frames saved in a day and never read.

**Before building anything here, understand what can and cannot be measured:**

| channel | ground truth | can recall be measured? |
|---|---|---|
| `@madovermarketing_mom` | `#Collaboration`, exact | yes — but **the model never runs there** (`verdictSource: 'rules'` on 79 of 79) |
| `@viralbhayani` | 5 human labels, plus the 60-post sample from 17 Aug | **thinly** — 78.6% recall, wide error bars at 14 positives |
| everything else | none | no |

So "real-time accuracy" cannot mean a live recall number — there is nothing to score against
minute to minute. What it CAN honestly mean, in increasing order of effort:

1. **A trend, not a number.** `accuracyHistory` (a `Setting` row, bounded at 30) already
   stores every run. Render the last N runs on `/paid-posts` with the RANGE, not a point
   estimate — a single run is a sample and the harness now says so.
2. **A scheduled run.** Put `ig:accuracy` on a cron (it costs ~2-3 cents) and surface the
   date of the last one. A figure with no date is the "freshness is not liveness" mistake.
3. **A real ground-truth loop.** The cross on `/paid-posts` writes a human ORGANIC, so every
   dismissal is a labelled negative. **The gap is positives** — dismissal-only labelling
   makes recall structurally unmeasurable from human answers, which is a real cost that was
   accepted knowingly on 17 August. If recall measurement matters, the sampled-audit
   approach used on 17 August is the honest instrument: take N posts, judge them
   independently, compare. It found 78.6% where the docs claimed 100%.

**Whatever is built: `ig:accuracy`'s `pred` changed to `final === 'CAMPAIGN'` on 17 August,
so numbers after that date are not comparable with any figure recorded before it.** Say so
wherever a trend is rendered, or the first frame-escalation will read as a regression.

## 4. "Dashboard simplified" — largely still to do

Only three things were done on 17 August: the duplicated per-recipient allowance block was
replaced with the one cap line that actually governs throughput; the dead
`messages/dispatcher.tsx` (182 lines, zero importers) was deleted; and `/paid-posts` went
from three lists showing the same posts to one table.

**MEASURED on the landing page before that work: 8 direct children, 11 blocks, ~26 always-on
prose blocks and 90-120 discrete numerals on a live day — against 6 controls.** The pace
panel alone renders 10 numbers and 0 controls.

Proposed target: **the switch · one health sentence · the single most important blocker ·
the draft queue · the cap line.** Everything else moves to `/rules`, which exists for exactly
this.

**Four constraints any simplification must satisfy — check these BEFORE editing:**

- **"Nothing happened with no explanation" is the failure this project keeps rediscovering.**
  Explanations must stay REACHABLE, not all on screen. Distinguish *delete* from *move
  behind a click*.
- **Each draft row keeps its refusal sentence on the COLLAPSED row**, not inside an expander.
  Measured 2026-08-06: all four waiting drafts would have been refused by a button that said
  nothing about it.
- **`tests/stopInventory.test.ts`** requires every gate stop to stay reachable with a remedy,
  and `tests/shell.test.ts` requires ≥6 authenticated pages.
- **`src/scripts/layout.ts` hardcodes each page's path, exact H1 and a query budget, and
  FAILS rather than skips.** Adding or renaming a page fails `ig:layout` until that array is
  updated. Run it after ANY UI change — presence, 200s and chunk-loading all passed once on
  a page whose layout was destroyed.

Also outstanding from before: `/` still issues ~454 queries against a 520 budget, and the
remaining count is the per-draft gate loop, which is the deliberate design. Reducing it means
batching the gate's own reads — real work, not a config change.
