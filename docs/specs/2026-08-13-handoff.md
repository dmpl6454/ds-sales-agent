### 3. Phase 4.3 — the burner's 70 pair rows

`@tabishmukaddam1` is `fleetMember: false` and holds 70 `OutreachPair` rows; since 2026-08-08
a pair row IS a live route.

**The trap the plan does not mention: `OutreachAttempt.pairId` is `ON DELETE CASCADE`.**
Deleting a pair deletes every attempt on it — and that record is what spacing, the
unanswered-touch cap and the new-material rule are derived from, so a bad delete lets the
system write to someone it has already written to. MEASURED: 0 of the 70 carry attempts, so a
delete is safe *today*; a delete PATH that can reach a pair with history is not. Whatever you
build must refuse a pair with any attempt, and must be a command (dry run by default), not a
one-off script — a script that no longer exists in the repo is how 21 ground-truth labels got
poisoned in August.

Two tests already assert the exclusion holds (`runOutreach` and `fleetRingFor` both scope to
`fleetMember`). This is tidy-up, not safety.

### 4. Phase 4.1 + 4.2 — ship TOGETHER or not at all

The plan is explicit and it is right. Removing the `autopilotEnabled` gate on
`detectThenDraft` takes drafting from **4×/day to 96×/day**; 4.2's cap is the only thing that
would bound the resulting queue, and today it does not bind at all
(`newBrandTouchesToday` counts DELIVERED messages and nothing has ever been delivered, so the
persistent half is permanently 0).

4.2 wants **two counters, both named** — first touches CREATED today and first touches
DELIVERED today — surfaced on `/rules` from the module that enforces them. Do not merge them
into one number.

Note what changed in your favour: `HOOK_STALE_SINCE_DRAFT` now catches a decayed claim at the
gate, so a larger queue is less dangerous than it was. It is not free.
