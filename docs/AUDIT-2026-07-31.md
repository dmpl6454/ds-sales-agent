## CRITICAL

### C-1. The dashboard is served to the whole network with no authentication

`EXECUTED`. The server binds all interfaces, not loopback:

```
lsof -nP -iTCP:3000 -sTCP:LISTEN   →  TCP *:3000 (LISTEN)
curl http://10.120.2.75:3000/      →  200
```

The LAN-served HTML contains the full control surface:

```
1  Send from @bollywoodsocietyy
1  Send from @madaboutmarketingg
1  Send from @bollywoodchronicle
2  Autopilot          4  Auto-send
16 Connect            9  Remove
```

There is **no `middleware.ts` anywhere** in the repo and **no auth code in
`src/app/`** — no session check, no basic auth, no allowlist, no origin restriction.

Anyone on the same Wi‑Fi — café, coworking space, office guest network, hotel — can
open that page and, with no credential:

- press **Send from @bollywoodsocietyy** and deliver a DM from a revenue account
- switch **Autopilot** on
- **Auto-send** any account, arming it for unattended sending
- **Remove** accounts and channels
- press **Connect**, which opens a Chrome window on the operator's machine
- press **Sync now**, running an unlocked slot (see H-4)

`actions.ts:242` already anticipates exactly this — *"A dashboard is a web page:
anyone who can reach it can call this action"* — and correctly puts
`AUTOPILOT_ENABLED` in `.env` as a floor the page cannot cross. That reasoning is
right and it stops at one switch. Everything else on the page is unprotected.

This is the highest-impact finding in the audit and it is a deployment property, not
a code bug: the safety model assumes a single trusted operator at the keyboard, and
nothing enforces that assumption.

**Fix:** bind loopback only (`next start -H 127.0.0.1`, and the same for `pnpm dev`).
That is a one-line change and closes the whole class. If it must ever be reachable
remotely, that needs real auth in front of it, not a bind change.

## HIGH

### H-1. The dashboard's Send button bypasses five checks that autopilot enforces

`CODE`. `deliverWaiting` (`src/outreach/deliver.ts`) re-checks **eight** conditions
before delivering a waiting draft. `sendNow` (`src/app/actions.ts:70`) checks
**three**.

| Re-check | `deliverWaiting` | `sendNow` |
|---|---|---|
| attempt still waiting | ✅ (atomic) | ⚠️ non-atomic — see H-2 |
| sender `ACTIVE` | ✅ | ✅ |
| `hasSession` | ✅ | ✅ |
| sender `autoSendEnabled` | ✅ | n/a (a human is present) |
| **`pair.enabled`** | ✅ `deliver.ts:83` | ❌ |
| **`target.optedOut`** | ✅ `deliver.ts:87` | ❌ |
| **target replied** | ✅ `deliver.ts:98` | ❌ |
| **`maxPerTargetPerDay`** | ✅ `deliver.ts:116` | ❌ |
| **`sender.dailyCap`** | ✅ `deliver.ts:120` | ❌ |

Consequences, in descending order of how much they matter:

1. **The reply halt is bypassable by clicking Send.** A reply is the governor's
   hardest stop — it halts every sender to that target. A draft prepared before the
   reply arrived still has a live Send button. The guard that was made functional
   today protects autopilot and not the button next to it.
2. **`optedOut` is bypassable.** `removeTarget` sets `optedOut: true` and tells the
   operator the channel *"can never be contacted again by accident"*
   (`actions.ts:550`). A READY draft's Send button still delivers. **That message is
   false as written.**
3. Daily caps and a disabled route are likewise bypassable.

I did not trigger a live send to demonstrate this, because doing so would mean
sending a real DM in violation of the guard being tested. The absence of the checks
is plain in the code and is not ambiguous.

**Fix:** extract the re-check block from `deliverWaiting` into one shared function
and call it from `sendNow` too. The duplication is the bug.

### H-2. `sendNow`'s idempotency guard is a non-atomic check-then-act

`CODE`. `actions.ts:79` reads `attempt.status`; `actions.ts:96` writes `SENDING`.
Between those two statements any concurrent caller passes the same check. The comment
above it asserts *"A double click cannot double send."* That is not what the code
does.

`deliver.ts:127` gets this right with an atomic conditional claim:

```ts
const claimed = await prisma.outreachAttempt.updateMany({
  where: { id: attempt.id, status: 'READY' },   // condition and write, one statement
  data: { status: 'SENDING' },
})
if (claimed.count === 0) { hold('already being sent'); continue }
```

Racers that reach `sendNow`: two operators on the LAN (C-1), one operator
double-clicking, or an operator clicking while a slot's `deliverWaiting` runs.
Outcome is two DMs to the same prospect seconds apart — the single worst spam signal
available.

**Fix:** use the `updateMany` + `count === 1` pattern in `sendNow`.

### H-3. Both send guards degrade to tautologies on a short multi-line body

`EXECUTED`. `distinctiveSlice` picks the middle line longer than 40 chars. If **no**
line exceeds 40 chars it falls back to the longest line — which for a short message
is **the greeting**, the exact text `matching.ts:17-19` documents as unsafe because
*"the greeting repeats the contact's name, which also renders in the thread header."*

Running the real logic on the real stored body of the chronicle send:

```
body:   "Hi Bollywood Chronicle,\n\nThis is a test message."   (48 chars, 0 lines >40)
needle: "Hi Bollywood Chronicle,"

post-send guard, message NOT delivered, page holds only thread chrome
  "Bollywood Chronicle  bollywoodchronicle  Active now  Hi Bollywood Chronicle, Message"
  → passes as "delivered": true          ← the guard CANNOT FAIL

composer read-back, paste lost everything after the greeting
  staged = "Hi Bollywood Chronicle,"
  → passes as "matches drafted body": true   ← a TRUNCATED message would be sent
```

Both of the two guards `CLAUDE.md` says *"must not be removed"* are defeated at once,
and this is the **same class of bug** the docs record as already fixed once
(*"A guard that reads the whole page can be a tautology"*). It came back through a
different door: not the page-text check, but the needle.

It is reachable through a supported action — the dashboard's edit box accepts any body
from 1 to 4000 characters — and **the one message that took this path in production
was the 12:27 chronicle send**, which was edited short in the dashboard.

Related dead end: a body whose longest line is under 15 chars yields `needle = null`,
so `messageMatchesOurs` always returns `false` and the composer guard can never pass.
Editing a draft to `"ok"` makes it permanently unsendable with the misleading error
*"composer content does not match the drafted message"*.

`EXECUTED` — precise trigger condition: no line >40 chars **and** the greeting is the
longest line.

**Fix:** exclude the first and last lines from the fallback as well as the primary
path (the function already documents why they are unsafe); require a minimum needle
length; and refuse to save an edit that cannot produce a distinctive needle, at edit
time, rather than failing opaquely at send time.

### H-4. `runSlot` has no lock, and an unauthenticated action calls it

`CODE`. Cron tasks pass `noOverlap: true`, which is per-task. `runSlot` itself has no
mutex, and `syncNow` (`actions.ts:37`) calls `runSlot('manual')` directly from the
LAN-reachable page.

Concurrent slots mean concurrent `runOutreach`. The governor's `hasPendingAttempt` is
a **read** (`plan.ts:108`) and the attempt is **created** later (`plan.ts:274`), so two
planners both see "no pending attempt" for the same pair, both create one, and both
dispatch. `deliverWaiting`'s atomic claim does not help — these are freshly created
attempts, sent inside the planner.

Racers: two `Sync now` clicks, `Sync now` during a cron slot, or `pnpm run:slot` while
the dashboard's embedded scheduler fires.

**Fix:** one advisory lock around `runSlot` (a `Setting` row with pid + timestamp,
checked the way `startScheduler` already checks its heartbeat via `process.kill(pid, 0)`).

### H-5. Checkpoint detection is URL-only and misses the most common enforcement

`CODE`. `assertNoCheckpoint` (`session.ts:104`) matches only `page.url()` against
`/challenge`, `/accounts/suspended`, `/accounts/disabled`, `/two_factor`.

Instagram's most common enforcement for DM activity — **"Action Blocked"**, "We
restrict certain activity to protect our community", "Try again later" — renders as an
**in-page modal on the current URL**. So does a suspension notice on a profile page.
None of those change the path, so none are detected, and the send proceeds.

That directly undercuts the rule the docs are most emphatic about: *"A checkpoint is
never retried."* The mechanism that classifies something as a checkpoint cannot see
the form enforcement usually takes. What actually happens instead is the send fails
some later check and is recorded as an ordinary failure, leaving the account `ACTIVE`
and eligible for the next slot — i.e. **retrying into a block**.

`UNVERIFIED` for the specific modal wording: I have not triggered a real Instagram
block and will not, so the exact strings need capturing when one occurs. The gap in
the detection method is `CODE`-certain regardless.

**Fix:** add a DOM/text check alongside the URL check for the known enforcement
strings, and treat "Message could not be sent" as a hard stop rather than a retryable
failure.

### H-6. A CHALLENGED account can be un-halted without anyone logging in or looking

`CODE`. `checkConnect` (`actions.ts:304`) sets `status: 'ACTIVE'` whenever the connect
flow reports `connected`, with the comment *"a fresh hand login is exactly what clears
a CHALLENGED account, and it is the only thing that should."*

But `connected` is returned on two paths where **no login happens**:

1. `startConnect` (`connect.ts:63`) — if the profile is already logged in,
   `loggedInAs` returns the handle immediately and it reports `connected`. Chrome opens
   and closes; nobody types anything.
2. `pollConnect` (`connect.ts:85`) — when no session is in the module Map (after a
   restart or hot reload) it returns `connected` purely from
   `profileStatus(handle).hasSession`, with no identity check at all.

So the sequence "Instagram flags the account → we set CHALLENGED → operator presses
Connect → status silently returns to ACTIVE" needs one click and inspects nothing. The
halt exists precisely because a human is supposed to look at the account first.
Reachable unauthenticated per C-1.

Path 2 is worse than path 1 because it also skips the wrong-account guard, and it
depends on `hasSession`, which is itself fail-open (M-1).

**Fix:** clear `CHALLENGED` only on an explicit, separate operator acknowledgement —
never as a side effect of a connectivity check.

### H-7. Two "already used campaign" queries disagree, producing a permanent lockout

`EXECUTED`. The same concept is computed twice with different filters:

- governor input, `plan.ts:80-87` — `where: { pairId, campaignId: { not: null } }`,
  **no status filter**
- hook selection, `plan.ts:229-240` — same, but restricted to
  `status IN (SENT, REPLIED, SENDING, READY, QUEUED)`

The second carries an explicit comment saying the first behaviour is a bug:

> *"SKIPPED and FAILED are excluded deliberately. 'Used' must mean the recipient has
> seen it… Counting those burned a campaign every time a draft was regenerated, so
> four discards would exhaust the pool and the pair would fall through to
> `no-new-material` with four perfectly good unused campaigns sitting there."*

**The fix was applied to the hook lookup and not to the governor's gate.** Measured on
live data right now:

```
madaboutmarketingg -> madovermarketing_mom
  campaigns burned per GOVERNOR (any status) : 2
  campaigns burned per createAndDispatch     : 0
  fresh CAMPAIGN rows in 72h window          : 4
  GOVERNOR unusedCampaignCount               : 2     ← gate sees 2
  what a hook lookup WOULD find              : 4     ← dispatcher sees 4
```

Two of four campaigns are already burned on that pair by drafts that were never
delivered. Every `pnpm run:slot` that skips a draft, and **every `pnpm burner on`**
(which mass-SKIPs drafts by design, `burner.ts:62`), burns more. At zero the pair is
reported `no-new-material` and can never send again despite fresh material sitting
there — a self-inflicted, silent, permanent lockout, and rehearsal mode accelerates it.

**Fix:** apply the same status filter to the governor's `unusedCampaignCount`. One
line, and it makes the two agree.

## MEDIUM

### M-1. `hasSession` is an OR, in a gate documented as fail-closed

`EXECUTED`. `profile.ts:131` — `SESSION_COOKIES = ['sessionid', 'ds_user_id']`, used as
`name in (?, ?)` with `count(*) > 0`. That is satisfied by **either** cookie.
`ds_user_id` is not a session; only `sessionid` is. A profile retaining `ds_user_id`
without `sessionid` reports `hasSession: true`, which:

- is autopilot switch #4, so it arms an account that cannot send
- is the sole basis of the `pollConnect` fallback in H-6

The docblock says this *"must fail CLOSED"*. The query is the loosest available.
(The live profile currently has both cookies, so this is latent, not active.)

**Fix:** require `sessionid`.

### M-2. Autopilot's own sends write no audit row

`EXECUTED`. `actions.ts` audits every send; `deliver.ts:161` audits every send;
`plan.ts applyOutcome` (`plan.ts:353`) audits **none**. The planner path is the
autopilot path.

```
AuditLog rows for the 14:00 cron-fired send to a real recipient:  (none)
```

`actions.ts:27` states *"Every state change writes an AuditLog row."* That is false for
the one path that runs with nobody present, which is the path where an audit trail
matters most.

**Fix:** write the audit row in `applyOutcome`.

### M-3. `SEND_JITTER_MIN/MAX_SECONDS` is dead config that promises pacing

`EXECUTED` — `grep` across `src/` finds no reader outside `env.ts`. The variables are
parsed, range-validated, and cross-checked (`env.ts:94`, `min <= max`), and `.env`
documents them as *"Human-like delay bounds between consecutive DMs, in seconds."*

There is **no delay between consecutive DMs anywhere.** Neither `deliverWaiting`'s
loop nor `runOutreach`'s loop pauses; `sendDm`'s `jitter()` covers only pauses *within*
one send. Multiple deliverable attempts fire back-to-back.

At 1–2/day this is academic. It matters because the config asserts a safety control
that does not exist, and the obvious next step (raising volume) is exactly when someone
will rely on it. Validated-but-unused config is more dangerous than absent config.

**Fix:** either honour it between sends, or delete it and stop advertising it.

### M-4. Three byte-identical bodies are queued to one target from three senders

`EXECUTED`. Needle-collision analysis surfaced this:

```
3 attempts share needle "I am checking that a multi-line message arrives intact: that"
  bollywoodchronicle->priyanshu123321123
  bollywoodsocietyy->priyanshu123321123
  madaboutmarketingg->priyanshu123321123
```

All three are `READY`, all 534 chars, all identical, all to the same recipient. If sent,
@priyanshu123321123 receives the same message three times from three accounts — the
precise repetition pattern decision 3 exists to prevent, seeded from `prisma/bespoke.ts`.

They are test drafts to an account we own, so nobody is harmed today. They are also
sitting behind live Send buttons on an unauthenticated page (C-1).

**Fix:** discard them; make the seed's test bodies distinct per sender.

### M-5. All four senders share one persona

`EXECUTED` (recorded last session, still open, repeated here for completeness). Every
`SenderAccount` carries *"Kapil Jain, Co-founder, Bollywood Society"*. A DM from
`@madaboutmarketingg` introduces itself as a different brand, and three revenue
accounts emit byte-identical intro and signature blocks. `addSender` (`actions.ts:367`)
actively propagates this by copying the persona from the oldest account.

Business-identity question; needs real names, not generated ones. See `CLAUDE.md`
decision 3b.

### M-6. The clipboard is a global unsynchronised resource in the send path

`CODE`. `copyToClipboard` → `pbcopy`, then `page.keyboard.press('Meta+V')`. The OS
clipboard is process-global with no lock. Two concurrent sends (reachable via H-4)
interleave as: A copies → B copies → A pastes **B's body**.

The composer read-back normally catches this (staged ≠ A's body). It does **not** catch
it when the two bodies share a distinctive needle — which is exactly the state M-4
describes. Guard-plus-guard, both defeated by the same underlying condition.

Two secondary issues in the same function: it is **macOS-only** (`pbcopy` and `Meta+V`
both), so the "host it somewhere that doesn't sleep" next step breaks the send path;
and the full pitch is left on the operator's clipboard indefinitely, which on macOS
syncs to their other devices via Universal Clipboard.

**Fix:** serialise sends; on non-Darwin use the platform clipboard and `Control+V`.

### M-7. An abandoned Connect window blocks all sending for that account

`CODE`. `MAX_AGE_MS` (20 min) is only enforced *when `pollConnect` is called*. Close
the dashboard tab with a Connect window open and nothing polls, so the window stays
open indefinitely holding Chrome's lock on the profile directory. `startConnect`
defensively calls `cancelConnect` first; `deliverWaiting` and `sendNow` do not, so
their `launchProfile` fails for that account until someone notices.

Fails visibly (a send error), not silently — hence MEDIUM.

**Fix:** sweep stale sessions on a timer, not on poll.

### M-8. `skipAttempt` has no status guard and can destroy send history

`CODE`. `actions.ts:577` sets `status: 'SKIPPED'` on any attempt id with no checks at
all. Applied to a `SENT` attempt it erases the record of a message a real person
received. That record is what `touchesSoFar`, spacing and the new-material rule are
computed from, so the system would then be free to write to someone it has already
written to — the exact outcome `CLAUDE.md`'s "removal never deletes send history" rule
exists to prevent. Applied to a `SENDING` attempt it corrupts the state of an
in-flight browser send.

Every sibling action (`sendNow`, `editAttemptBody`, `markSent`) guards its transition.
This one does not, and it is callable unauthenticated.

**Fix:** restrict to `READY`/`QUEUED`, as `editAttemptBody` already does.

### M-9. `markSent` accepts almost any prior status

`CODE`. `actions.ts:158` returns early only if already `SENT`. So `FAILED`, `SKIPPED`,
`SENDING` and **`REPLIED`** can all be flipped to `SENT`. Flipping `REPLIED` keeps
`repliedAt` but changes the status, desynchronising the two: status-based queries
(`view-model.ts:216`, `plan.ts:95`) stop seeing the reply while `repliedAt`-based ones
still do. It also increments `timesUsed` on the variant each time it is called.

**Fix:** allow only from `READY`/`QUEUED`/`FAILED`; make it idempotent.

### M-10. Schema default and documented default disagree on spacing

`EXECUTED`. `schema.prisma:94` — `cooldownDays Int @default(5)`. `env.ts:59` —
`DEFAULT_COOLDOWN_DAYS: intish(7, …)`. `CLAUDE.md` says 7 "is the value actually in
force", which holds only because `addSender`/`addTarget` pass it explicitly. Any other
insert path — a seed change, a manual insert, a future migration — silently gets 5 days
of spacing while every document says 7.

**Fix:** make the column default 7 so the two cannot drift.

- **No SQL injection surface** — no `$queryRaw`/`$executeRaw` anywhere. `EXECUTED`
- **No XSS surface** — no `dangerouslySetInnerHTML` or `innerHTML` in `src/app/`.
  `EXECUTED`
- **The autopilot env floor is correctly implemented.** `settings.ts:69` is

- **The governor is genuinely pure and well tested** — 30 tests including the exact
  spacing boundary, ceiling-of-0, ceiling-of-null, rule precedence, and two-senders-

  rather than retrying. `EXECUTED`

  check that catches Instagram serving HTML with HTTP 200. `CODE`

### Suspicions I had that were wrong

Recorded so the list is not just confirmation of my own guesses:

- I expected **no confirmation on Remove**. Wrong — both `accounts.tsx:202` and
  `channels.tsx:108` implement a two-step inline confirm with an accurate explanation.
- I expected the **connect polling interval to leak**. Wrong — `accounts.tsx:74`
  clears on unmount *and* on state change, with a comment explaining why.
- I expected `distinctiveSlice` to pick the **shared persona line** as the needle for

  survived. Worth noting as a method lesson, not just an anecdote.

## Addendum — deploying to Linode, with dashboard login

Added after the main audit, in answer to: *"anyone with the code, deployed to Linode,
should be able to connect an account (with 2FA) and have it work."*

**Short answer: no, not as it stands.** The send path is macOS-only in two places, the
browser cannot launch on a headless box, and the Connect flow's core premise — a human
typing into a visible Chrome window — does not survive being on a remote server. The
main audit under-rated these because it ranked findings by blast radius on the
accounts, not by "does this run on Linux."

Below, `D-n` findings are new or re-severitised for this deployment.

### D-1. BLOCKER — every send fails on Linux: `pbcopy`

`CODE`. `src/lib/clipboard.ts:17` is `spawn('pbcopy')`. `pbcopy` is a macOS binary; on
Linux this throws `ENOENT`. `sendDm.ts:136` calls it immediately before the paste, so
**no message can be sent on a Linux host at all**. This is M-6 in the main audit, where
it was ranked MEDIUM as a portability note. For Linode it is a total blocker.

**Fix:** branch on `process.platform` — `pbcopy` (darwin), `xclip -selection clipboard`
or `wl-copy` (Linux). `xclip` needs the same X display as Chrome, so it has to be
installed alongside Xvfb.

### D-2. BLOCKER — the paste modifier is wrong on Linux: `Meta+V`

`CODE`. `sendDm.ts:137` is `page.keyboard.press('Meta+V')`. In Playwright/Patchright
`Meta` is Command on macOS and the **Super key** on Linux. Paste on Linux is
`Control+V`. So even with D-1 fixed, the paste does nothing.

It does at least fail *safe*: the composer read-back at `sendDm.ts:143` finds an empty
composer, refuses, and nothing is delivered. The result is a system that never sends
and reports "composer content does not match the drafted message" every time — correct,
but the cause is not discoverable from that message.

**Fix:** `page.keyboard.press('ControlOrMeta+V')`, which Playwright resolves per
platform. One token.

### D-3. BLOCKER — `headless: false` cannot launch without a display

`CODE`. `session.ts:90` sets `headless: false`, and `CLAUDE.md` requires that always
(a headless Chrome differs measurably, which is a sound reason). A Linode instance has
no X server, so Chrome will not start.

This is solvable and does **not** require weakening the rule: run a virtual display.
`Xvfb :99` plus `DISPLAY=:99` gives real, non-headless Chrome with a genuine
framebuffer. Chrome cannot tell the difference; the anti-detection properties are
preserved. `xvfb-run -a pnpm start` is the crude version.

Also `session.ts:89` sets `channel: 'chrome'` — the **real Google Chrome**, not
Chromium. `google-chrome-stable` must be installed on the box. Chromium is explicitly
rejected for having a distinguishable build, so do not substitute it.

### D-4. BLOCKER for your stated workflow — Connect cannot be completed remotely

`CODE`. This is the important one and it is architectural, not a bug.

`startConnect` opens Chrome and leaves it open for a human to log in — *"the human
still types the password into Chrome's own form; nothing here reads it"*
(`connect.ts:16`). That is the whole safety argument and it is correct. But on Linode
that Chrome window renders on the **server's** display. The operator sitting at their
own laptop has no way to see it or type into it — including the 2FA code.

So the sequence you described — *log in bollywoodchronicle, complete 2FA, press
Connect, it works* — has no path on a remote host as the code stands. The dashboard
will report `waiting: "Log in in the Chrome window that just opened"` for twenty
minutes and then time out, and there is no window the operator can reach.

Options, in order of how much they preserve the design:

1. **Xvfb + noVNC/VNC into `:99`.** The operator opens a browser tab, sees the real
   Chrome running on the server, and types the password and 2FA code into it directly.
   Device identity, login event and IP all belong to the server — consistent, and the
   only option where the profile is created where it will be used. Needs VNC locked
   behind auth or an SSH tunnel; an open VNC port is worse than D-5.
2. **X11 forwarding over SSH** (`ssh -X`), running the connect flow as a CLI
   (`pnpm ig:login <handle>`). Same effect, no persistent VNC surface, but the window
   is fragile over a slow link and 2FA is time-boxed.
3. **Log in locally, then move the profile directory.** *Do not do this.* It is a
   `storageState`/profile transplant by another name — the profile would carry device
   identifiers minted on one machine and network and then appear on another, which is
   precisely the signal `profile.ts:14-24` says the entire design exists to avoid.

### D-5. C-1 gets worse on Linode, and my recommended fix would lock you out

`EXECUTED` (on the current host) + `CODE`. On a laptop, binding `*:3000` exposes the
dashboard to the local network. On a Linode it exposes it **to the public internet** —
any port scan reaches a page with live `Send from @bollywoodchronicle` buttons, an
Autopilot toggle and Remove controls, with no authentication.

Note the interaction: the fix I recommended in C-1 — bind `127.0.0.1` — is still right,
but on a server it also means the operator cannot reach the dashboard at all. So for
Linode the fix is two parts:

- bind loopback only, **and**
- reach it through an SSH tunnel (`ssh -L 3000:127.0.0.1:3000`), or a reverse proxy
  (Caddy/nginx) terminating TLS with real authentication in front.

Whichever is chosen, "publicly reachable with no auth" must not be the deployed state
for even a short window, because the exposure is a send button on a revenue account.

### D-6. NEW — an account with 2FA can be spuriously marked CHALLENGED mid-send

`CODE`. Not in the main audit; found only when you mentioned 2FA. This one matters
because it is triggered *by* the setup you described.

`session.ts:29-34` lists `/two_factor` as a **checkpoint path**, and
`assertNoCheckpoint` is called **five times inside a single send** (`sendDm.ts:86, 92,
126, 129, 164` — including immediately after pressing Enter). So if Instagram re-prompts
for a 2FA code at any point during a send, the account is marked `CHALLENGED`, every
pair using it halts, and by design nothing retries.

That is the same mistake the codebase already diagnosed and fixed for the login form.
`session.ts:36-49` explains it at length:

> *"A login form is NOT a checkpoint, and conflating the two was a real bug… an
> operator who sees CHALLENGED three times for something that just needed a fresh
> login learns to dismiss it, and then dismisses the one that matters."*

`/accounts/login` was moved out of the checkpoint list for exactly that reason.
**`/two_factor` was left in.** A 2FA re-prompt is the same category of event: routine,
expected, and resolved by a human entering a code — not Instagram taking action against
the account. On accounts with 2FA enabled it will recur.

Worse in combination with D-4: the recovery for a `CHALLENGED` account is to connect it
again, and on Linode connecting is the thing that does not work yet.

**Fix:** move `/two_factor` from `CHECKPOINT_PATHS` to a third state — "needs a human to
enter a code" — that pauses the send without marking the account as flagged. It should
*not* simply join `LOGIN_PATHS`, because the remedy differs: a login form means
re-authenticate, a 2FA prompt means an existing session is being re-verified.

### D-7. The Chrome profile directory must outlive every deploy

`CODE`. `~/.ds-sales-agent/chrome-profiles/<handle>` holds `mid`, `datr`, `ig_did` —
the device identity that is the load-bearing safety property, and which
`profile.ts:46-52` records as **unrecoverable** once destroyed.

On a laptop this is automatic. On a server it depends entirely on deployment shape:

- git pull + restart on a persistent filesystem — safe, the directory is in `$HOME`
- **Docker/container without a mounted volume — destroyed on every release.** Each
  deploy makes all three accounts look like brand-new hardware to Instagram, which is
  the precise state the whole design avoids
- baking the profile into an image, or rsyncing it between hosts, is the transplant
  from D-4 option 3 — same objection

Also: `homedir()` resolves to the *service user's* home. If the app runs as `www-data`
via systemd with `ProtectHome=yes`, the path silently becomes unwritable or ephemeral.

**Fix:** pin the location explicitly, mount it as a volume, back it up as a credential
file (it is decryptable offline — `profile.ts:60-65`), and assert at boot that it is
writable and persistent rather than discovering otherwise at send time.

### D-8. Detection will likely degrade from a datacenter IP, and that cascades

`CODE` + `UNVERIFIED` on the exact threshold. `feed.ts` hits Instagram's anonymous feed
endpoint with no credentials — correct, and decision 4 holds. But Instagram rate-limits
and blocks **datacenter ASNs** far more aggressively than residential ones, and
`feed.ts:130` treats 429 as "back off, retry next slot".

Decision 5 means detection failing does not block outreach — a message is still
prepared. But with no `CAMPAIGN` verdicts ever recorded:

- `unusedCampaignCount` stays 0, so `NO_NEW_MATERIAL` blocks **every follow-up**
- only first touches can ever be sent
- and per H-7, the governor keeps burning campaigns on skipped drafts, so the pool
  shrinks and never refills

The result is a system that appears healthy, sends the first message to each pair, and
then silently stops — with `no-new-material` as the only clue. I have not measured how
quickly a Linode IP gets throttled, so the trigger point is unverified; the cascade
once it happens is not.

### D-9. `connect.ts`'s in-memory Map constrains the process model

`CODE`, and `CLAUDE.md` already flags it. Connect state lives in a module-level `Map`,
so it only works if the process that served `startConnect` also serves `checkConnect`.
That holds for a single `next start`. It breaks under PM2 cluster mode, multiple Node
workers, or any horizontal scaling — and it breaks if the dashboard and `pnpm worker`
run as separate processes and the poll lands on the wrong one.

Fails visibly (`"No connection in progress"`), not silently. But combined with the
`pollConnect` fallback in H-6, a restart mid-connect can report `connected` from a stale
cookie without any identity check.

**Fix for Linode:** run exactly one process (`EMBEDDED_SCHEDULER` defaults to on, so the
dashboard carries the scheduler — do not also run `pnpm worker`), and document that as
a constraint rather than leaving it to chance.

### D-10. `pnpm send`, the manual fallback, is macOS-only

`CODE`. `src/scripts/send.ts:135` shells out to `open` / `open -a <browser>`. Both are
macOS. On Linux this fallback is unavailable — which matters because it is the documented
escape hatch when the automated path fails.

**Fix:** `xdg-open` on Linux, or drop the browser-opening step and just print the URL.

### What genuinely does work on Linode

Verified, so it does not need to be on the worry list:

- **Timezone and day-window logic is portable.** `time.ts` computes everything through
  `Intl.DateTimeFormat` with an explicit `timeZone`, and `istDayStart` derives the real
  zone offset rather than reading process-local time (`time.ts:55-84`). A UTC server
  produces correct IST slots and correct daily cap windows. `EXECUTED`
- **The scheduler is a better fit on a server than on a laptop.** The sleep-through-slot
  problem fixed today (`execution:missed`) largely disappears, because servers do not
  suspend. This is a real argument in favour of the move.
- **Detection needs no credentials**, so running it from a VPS adds no *account* risk on
  that path — only the IP-level exposure in D-8.
- **`better-sqlite3`** is native but builds cleanly on Linux with standard build tools.

### The conflict that is not a bug

`CLAUDE.md` decision 1 states, as a requirement still in force: **"Same home
residential IP the accounts normally use. No VPS, no VPN."** Linode is a datacenter IP,
so deploying there contradicts the single choice the research identified as load-bearing
— device and network identity continuity, described there as *"a pass/fail gate, not a
score."*

Two things follow, and I would rather state them plainly than let the deployment work
imply they are solved:

1. If the accounts are logged in *from* the Linode, the login event itself originates
   from a datacenter ASN. That is a new network identity for those accounts, on the
   first action taken from it.
2. The obvious mitigation is refuted in the same document: residential proxies and
   anti-detect browsers *"convert a normal pattern into an evasion pattern"*. So there
   is no clean fix available — only a real trade.

None of this makes the deployment work below wrong; D-1 through D-10 need doing whatever
the host is. But "it runs on Linode" and "it is as safe on Linode" are different claims,
and only the first is achievable by fixing code. This is your call to make, not mine —
I am flagging it once, clearly, and the plan proceeds either way.
