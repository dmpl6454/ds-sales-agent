# DS Sales Agent — Code Audit, 9 October 2026

**Scope.** The repository at `f9fc59c` (`main`), read against the rules CLAUDE.md says the code
enforces. **The live system was not reachable** from the audit container — no database, no Macs, no
Linode — so nothing here is a measurement of production. Every item is a defect in the code as
committed, with the path by which real inputs reach it.

**Method.** Typecheck and the full suite run in a clean container. Eleven independent reviewers each
read one lens of the code in full (send path and locks, browser driving, rules parity, templates,
detection, auth and API, deploy and installer, dashboard honesty, test vacuity, data and
concurrency, agent passes and health). **Every finding below was then re-traced by hand in the cited
file before it was kept.** The planned three-skeptic verification and the completeness critic did not
run (session and credit limits), so this report rests on one finder plus one manual trace per item.

**Baseline.** Typecheck clean. **140 test files, 2,360 tests, all passing.** None of the defects below
is caught by the suite; the "Tests that cannot fail" section says why for the ones that should be.

| severity | count | meaning |
|---|---|---|
| critical | 4 | a message can reach the wrong person or an answered thread, or irreplaceable data is deleted |
| high | 11 | real work silently halts, an operator is misled into harm, or a real security weakness |
| medium | 27 | incorrect behaviour with a bounded blast radius |
| low | 19 | latent or defensive |

## Critical

**C1. The inbox route can deliver the pitch to a different account.**
`src/outreach/browser/messageEntry.ts:60-62, 268-282`. When a profile offers no Message button and no
"Send message" in the … menu, the send types the handle into the inbox To: box and clicks the first
`span` in the dialog matching `/^handle$/i`. The match is case-insensitive and is tested against any
span, including a result row's display name. CLAUDE.md's own live pair shows the shape: @tips and
@tips_india both display "TIPS". If Instagram ranks the wrong row first it is clicked, Chat opens that
thread, the composer read-back passes (same bytes), and Enter delivers from a revenue account.
Nothing after the click checks who was selected.
*Fix:* match the username line only, case-sensitively, and read the thread header after Chat; abort
unless it equals the handle.

**C2. A fresh reply is swallowed and the follow-up goes into the answered thread.**
`src/outreach/replyCheck.ts:373-389`. If the recipient has an older reply row with `replyText: null`
(the inbox phase writes exactly that for "X sent an attachment" and "2 new messages",
`replyCheck.ts:700`), `checkConversation` writes the NEWEST bubble's text onto that old row, stamps
`replyCheckedAt`, and returns `no-reply` before `fresh` is computed (`:391`). The new reply is never
recorded with its own date, the 7-day halt does not re-arm, and the pre-send read reports the thread
clear.
*Fix:* compute `fresh` first, backfill only with a bubble that is not fresh, and record any fresh reply.

**C3. Removing a watched channel deletes its whole post corpus.**
`src/app/actions.ts:2297-2312`, `prisma/schema.prisma:353`. `removeTarget` hard-deletes whenever the
target has no SENT or REPLIED attempt, which is always true of a WATCH channel, and
`DetectedCampaign.target` is `onDelete: Cascade`. Pressing Remove on @viralbhayani deletes 1,000+
posts, their human labels and frame text, none of which can be re-scraped past the 48-post window.
The confirm strip says *"has never been messaged, so it will be deleted outright"*
(`src/app/channels.tsx:134`). CLAUDE.md (17 Aug) says in capitals not to delete these rows. The same
predicate also deletes a prospect whose only attempts are `not-in-thread` parks or in-flight rows,
cascading the record of a message the recipient may hold.
*Fix:* refuse the hard delete when any `DetectedCampaign` or any `OutreachAttempt` exists; retire
instead (`optedOut`, `watchEnabled: false`).

**C4. Two Macs can share one identity, and then both send at once.**
`src/lib/deviceEnrol.ts:160-167`, `src/outreach/devicePresence.ts:33`,
`src/outreach/dispatcher.ts:266-272`. A device name is never checked for uniqueness, the installer
pre-fills it from `scutil --get ComputerName`, and `deviceId()` is that name. Two Macs called alike
are BOTH the selected sending Mac. Each reads the other's lock row as local, asks its own OS whether a
foreign pid is alive, gets "no", and takes the lock — the two-dispatchers defect the 10 September
device field was added to close. Revoke matches on the name too (`deviceEnrol.ts:382`), so revoking
one Mac's key removes both.
*Fix:* refuse a name already paired or pending in `startEnrolment`; revoke by key fingerprint.

## High

**H1. The planner's fleet ring is unfiltered, so the marketing page can hold a bollywood recipient's
turn forever.** `src/outreach/plan.ts:347-355, 725-729`, `src/outreach/categories.ts:388-390`. The
planner builds each recipient's ring from raw pair rows and `whoseTurn` uses a pre-loaded ring
verbatim. Only `fleetRingFor`, `whoseTurnForMany` and `handOff` apply `ringMembersFor`, the 26 August
category filter, although `whoseTurn`'s docblock says the pre-loaded ring "never buys a different
verdict". @madaboutmarketingg still holds pair rows to bollywood companies (kept on purpose). Once
elected for one of them its route is refused `different-category`, every other page is
`not-this-senders-turn`, and the turn only advances on a delivery that cannot happen.
`src/app/view-model/rest-tally.ts:702` has the same shape.
*Fix:* filter `args.fleet` through `ringMembersFor` inside `whoseTurn`.

**H2. A recipient handle starting with "challenge" halts the whole fleet for 24 hours.**
`src/outreach/browser/session.ts:29, 163`. `classifyUrl` tests `url.includes('/challenge')` and the
profile URL is `instagram.com/<handle>/`. `assertNoCheckpoint` runs right after the profile loads on
both the send and read paths, the account is marked CHALLENGED, and the breaker stops every account.
The draft stays READY and trips it again after a person clears it.
*Fix:* match whole path segments of `new URL(url).pathname`.

**H3. The production frame path skips the publisher-watermark strip, and every ORGANIC post with frame
text is judged twice.** `src/detection/detectors/semantic.ts:610-625`,
`src/detection/pipeline.ts:308, 335`, `src/detection/judge.ts:227, 289`. `semanticDetector.classify`
runs its own caption → OCR → frame call → `applyFrameSignal`, without `stripOwnMarksFromFrame` and
without the `optedOut` gate; both live only in `judge.ts`. Its escalated CAMPAIGN is then handed to
`judgeWithFrame` as the caption verdict and accepted as `caption-decisive`. The 21 August fix for
@filmygyan's own watermark reading as a paid placement therefore does not apply on the path that
judges new posts. ORGANIC posts get two OCR reads and two model calls, two chances for a
non-deterministic model to escalate, and contradictory `frame:*` signals. A false CAMPAIGN also funds
a message under the material allowance. `tests/one-judging-path.test.ts:33` hard-codes three callers
and never reads `semantic.ts`, which is why this passes.
*Fix:* make `semanticDetector.classify` return the caption verdict only and leave the frame to
`judgeWithFrame`.

**H4. The sign-in page is an open redirect.** `src/lib/safe-next.ts:32-38`. `safeNext` rejects `//`
and backslashes but not control characters. `/\t/evil.com` passes and the browser's URL parser
resolves it to `https://evil.com/` (reproduced with Node's WHATWG `URL`). An operator who signs in from
a crafted link is sent off-site right after typing real credentials.
*Fix:* reject `/[\x00-\x1f\x7f]/` and check the resolved origin.

**H5. A first-touch introduction is delivered to a recipient who has since replied to another page.**
`src/outreach/gate.ts:902-904, 640-690`. The gate recomputes `isFollowUp` from live rows but uses it
only for the same-day, template-unset and date-only stops; nothing checks that the stored bytes are a
follow-up body. With `replyHaltScope = pair`, a queued introduction from page B goes out as the
introduction to a company already in conversation with page A — the message Tabish ruled must never
be sent after a reply.
*Fix:* refuse `isFollowUp && storedBody === fleetTemplate.body` with a discard remedy.

**H6. Removing a sender moves its follow-ups onto pages with no history, where they go out as first
messages.** `src/outreach/handOff.ts:17, 206-218`. The hand-off recomputes `touchNumber` from the
receiving pair but transfers `renderedBody` untouched. Its premise ("every waiting draft is the same
standard template") has been false since follow-ups shipped on 1 September. The update also has no
status guard, so a draft the dispatcher claimed SENDING mid-hand-off is rewritten to READY under a new
sender while the old account's browser pastes it.
*Fix:* discard a moving draft with `touchNumber > 1` when the receiving pair has delivered nothing,
and write with `updateMany` conditioned on the movable statuses.

**H7. A reboot can bring the dashboard back pointed at a deleted build.** `scripts/deploy.sh:299, 363`.
Deploys alternate `NEXT_DIST_DIR` between `.next-a` and `.next-b` and delete the old directory; nothing
in the repository runs `pm2 save`. The dump saved by hand on 9 September names whichever directory was
live then, so after an odd number of deploys a boot-time `pm2 resurrect` (the standing 2 GB resize
reboots the box) starts Next against a missing directory and pm2 crash-loops it. Separately
`.active-dist` is written before the reload and health check (`:230`), so after the documented
rollback the next deploy deletes the directory the workers are serving.
*Fix:* `pm2 save` at the end of the remote block; derive the active directory from `pm2 jlist` and
write the marker only after the 200.

**H8. On the hosted dashboard the queue says Autopilot is off while the switch above it says ON.**
`src/app/view-model/messages-page.ts:587, 591, 617`. The queue reads `settings.autopilotEnabled`, which
is env-floored and therefore false on the Linode by design; the switch reads `autopilotFleetWide`.
Every hosted view of the queue reads "waiting only for Autopilot to be switched on" about a fleet that
is sending.
*Fix:* use `autopilotFleetWide` for these three display reads.

**H9. Five screens describe a fleet-wide reply halt; the gate holds only the page that was answered.**
`src/app/page.tsx:226` (added by PR #1), `src/app/view-model/blockers.ts:173`,
`src/app/rules/page.tsx:180`, `src/app/view-model/rest-tally.ts:192`, `src/app/prospects/list.tsx:236`,
against `replyHaltScope = 'pair'` since 1 September. Readers are told every page pauses while rotation
elects another page into the same inbox inside the week.
*Fix:* derive each sentence from `settings.replyHaltScope`.

**H10. The all-held dispatcher re-takes the fleet lock back to back.** `src/agent/index.ts:780-784`,
`src/outreach/deliver.ts:136, 214`. When every draft is held (the documented steady state) a tick walks
the whole queue through the gate under the lock, and a tick longer than 30 s is followed immediately
by the next because the loop sleeps only the remainder. Over the tunnel this holds the lock almost
continuously, and the reply sweep and disk care in the same process land in the gap only by luck.
*Fix:* sleep the full poll interval after a tick that drove nothing.

**H11. A device agent whose every tick throws still reads as a healthy sending Mac.**
`src/agent/index.ts:614, 648, 776`. Presence is written before dispatch, `dispatchState` is simply not
rewritten, and nothing renders its age; the only record is a log line. Liveness versus success is
alarmed for detection and planning but not for the one process that sends.
*Fix:* stamp a dispatch success time after each tick and alarm on a fresh beat beside a stale stamp.

## Medium

**Sending and the send path**

- **M1. A database error between the READY→SENDING claim and the drive parks a never-driven draft as
  "may be delivered".** `src/outreach/deliver.ts:361-383`, `src/outreach/reservations.ts:123-130`.
  The exception leaves the row SENDING, the orphan sweep files it `not-in-thread`, and discard,
  re-queue and the removed settle UI all refuse that code, so the pair is held until someone edits the
  database. *Fix:* revert SENDING→READY and release claims in a try/catch, in `deliverWaiting` and
  `sendNow`.
- **M2. Pre-send thread reads are browser drives the tick neither counts nor re-asks about.**
  `src/outreach/deliver.ts:239-312, 342-359`. The autopilot and sending-Mac re-asks sit after the read
  block, and every hold `continue`s to the next draft's read, so a run of stale follow-ups keeps
  opening Chrome after the switch goes off. *Fix:* re-ask both before the read and count it as a drive.
- **M3. The dashboard Send button skips the pre-send thread read.** `src/app/actions.ts:188, 280`.
  Only `deliverWaiting` calls `ensureConversationChecked`, so a follow-up sent by hand can land in an
  answered thread the dispatcher would have held. `/rules` states the opposite.
- **M4. Send on the hosted dashboard always ends in a false sentence.** `src/app/actions.ts:206-301`.
  The claim, reservations and a send-start audit row are written before `withSendLock` refuses on
  `SEND_ENABLED=false`, and the null return reads "Another message is being sent right now".
- **M5. An enforcement modal after Enter returns the draft to READY.** `src/outreach/browser/sendDm.ts:285-289`,
  `src/outreach/deliver.ts:522`. The message may have been delivered; after `clearChallenge` the same
  body is sent again. *Fix:* park as `not-in-thread` when the CheckpointError follows Enter.
- **M6. Accepting a message request, then sending the cold pitch unread.**
  `src/outreach/browser/sendDm.ts:167-171`. The request exists because the recipient wrote first; a
  first touch skips the thread read, so an inbound lead's first answer is the template.
- **M7. A vanished recipient costs up to three drives per page on follow-ups.**
  `src/outreach/deliver.ts:239` precedes the anonymous probe at `:443`, and `readThread.ts` has no
  "page isn't available" branch, so the read parks `unreadable` and `TARGET_UNREACHABLE` never arms.
- **M8. `releaseSendLock` deletes whichever lock row exists.** `src/outreach/dispatcher.ts:341-343`.
  A Mac that stopped beating mid-sweep and later wakes deletes the lock another Mac has since taken.
  *Fix:* release on `value = ours`.
- **M9. A standby Mac's disk care takes the fleet send lock.** `src/outreach/dispatcher.ts:564`. The
  exemption lets a standby prune acquire the shared lock and poll it at 1 Hz, so the selected Mac
  waits for the prune.
- **M10. SIGTERM exits the agent mid-drive.** `src/agent/main.ts:12-17`. `stopDeviceAgent` sets a flag
  and `process.exit(0)` follows immediately; `launchctl unload` on every reinstall and the DMG update
  path (`scripts/dmg/install.sh:109, 328`) therefore cut a send in flight, which the orphan sweep parks
  for a person. The installer never checks the `sendLock` row as rule 8 requires.
- **M11. `editAttemptBody` can replace a body under a live send.** `src/app/actions.ts:641-691`.
  Check-then-write; the stored SENT body can differ from what was delivered.

## What was verified sound

These were traced and hold: the atomic READY→SENDING claim; the just-in-time autopilot and sending-Mac
re-asks immediately before it; `recordSend` never returning a delivered row to READY; the
`DailyReservation` test-and-set; the foreign-holder rule in `decideSendLock` and the conditional
takeover; the nested-lock refusal; the orphan sweep's pid+device guard and dwell; `OVERRIDABLE_BLOCKS`
being exactly the reply halt and dropped when unattended; opt-out, verified-only (NULL refused),
cross-fleet, same-day follow-up, material allowance and identical-message rules at both the governor
and the gate; the reply-halt query shared by all enforcers; decision 4 (no session on any detection
request, one transport, one identity); the anonymous-read gate's scopes and persistence; the
caption-first, footage-may-only-escalate rule in `judge.ts`; deny-by-default middleware; all 39 server
actions calling `requireOperator()` first; hashed session tokens with enforced expiry; scrypt passwords;
the ed25519 key validation and forward-only `authorized_keys` restrictions; deploy builds checking exit
codes directly; pm2 commands named, never global; dry-run defaults on every mutating CLI; IST day and
hour boundaries through `time.ts`; and the build-watch reloader.

## Recommendations, in order

1. **Close the four critical paths first** (C1–C4). Each is a few lines: a case-sensitive username
   match plus a header check; compute fresh replies before backfilling; refuse hard deletes of
   anything with posts or attempts; refuse duplicate device names.
2. **Make the planner's ring and the ring-complete rest category-aware** (H1, M12). H1 is the most
   likely live cause of recipients that never get written to.
3. **Remove the semantic detector's private frame path** (H3), so every new post goes through
   `judgeWithFrame` with the watermark strip and the opt-out gate.
4. **Make the screens read the rule in force** (H8, H9, M18–M21): `autopilotFleetWide` for display,
   `replyHaltScope` for every reply sentence, the sending Mac in the blocker list.
5. **Harden deploy and install** (H7, M22, M23, M10): `pm2 save`, resolve the host alias, chmod the
   `.env`, and drain the agent before exit. Then replace the hard-coded file lists in the guard tests
   with discovery, so the next caller nobody greps is caught.
